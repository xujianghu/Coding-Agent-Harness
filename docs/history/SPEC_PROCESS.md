## 一、Brainstorming 关键节点

### 1.1 智能体追问的关键问题

| 序号 | 问题 | 我的回答 | 影响 |
|------|------|---------|------|
| 1 | 运行形态是什么？（CLI/Web/混合/后台） | CLI 编码助手 | 决定了整个架构方向——纯 CLI 项目 |
| 2 | 用什么编程语言？ | TypeScript | 影响后续所有技术选型、分发方案、工具链 |
| 3 | 对接哪个 LLM 供应商？ | 多供应商支持 | 提升了 LLM 抽象层的复杂度，但也增加了设计深度 |
| 4 | 六个维度中哪个作为重点？ | 治理护栏 | 决定了资源分配和深度实现方向 |
| 5 | Agent 应具备哪些工具？ | 完整编码工具集 | 覆盖完整闭环，但增加了工具系统实现量 |
| 6 | 记忆系统做到什么程度？ | 先质疑规则，再选轻量增强 | 体现了对项目要求的批判性阅读 |

### 1.2 让我修正原设想的问题

**记忆系统边界的质疑（第 6 轮）**：

> AI 问："记忆系统做到什么程度？"
>
> 我没有直接回答，而是先质疑了项目要求：§4.2(D) 说"若以记忆为重点，其存储与检索必须自己实现"。既然我选的不是记忆，那是否有其他约束？
>
> 经过确认：**"不得接用框架自带 memory"的约束仅针对重点维度**。非重点维度只需"可运行的最低实现"，可以用底层库。
>
> 这让我将记忆系统从"可能需要从零实现"调整为"轻量增强（JSON 文件 + 关键词检索）"，节省了大量精力。

### 1.3 架构方案选择

AI 提出了三种方案：
- 方案 A：单体管道式 CLI
- 方案 B：分层插件式架构
- 方案 C：CLI + 内嵌 Web 服务

我选择了方案 B。方案 C 会增加架构复杂度，纯 CLI 更聚焦核心机制实现。

## 二、三轮关键迭代

### 迭代 1：定位与边界收敛

**对话节选**：
> AI：运行形态？（CLI/Web/混合/后台）
> 我：CLI 编码助手
>
> AI：语言？
> 我：TypeScript
>
> AI：LLM 供应商？
> 我：多供应商

**决策**：这三轮快速收敛了项目的核心定位——一个 TypeScript 编写的、支持多供应商的 CLI 编码助手。粒度适中，不贪大求全。

### 迭代 2：深度与广度取舍

**对话节选**：
> AI：六个维度中，你选择哪个作为重点深入？
> 我：治理护栏
>
> AI：Agent 工具集范围？
> 我：完整编码工具集
>
> AI：记忆系统程度？
> 我：等等，先搞清楚非重点维度的约束…

**决策**：这一轮的核心是"取舍"——明确重点（治理）和非重点（记忆）的投入比例。对记忆系统约束的质疑是本次迭代中最有价值的行为。

### 迭代 3：架构设计逐段审查

**对话节选**：
> AI：（呈现模块划分与职责表）
> 我：符合预期
>
> AI：（呈现四类机制设计）
> 我：合理
>
> AI：（呈现治理护栏深入设计）
> 我：可以
>
> AI：（呈现数据模型与凭据设计）
> 我：OK

**决策**：逐段审查的方式确保了每个设计决策都有明确确认，避免了"一次性呈现大方案后被忽略的细节"。

### 我推翻或修正的 AI 建议

| 建议 | 修正理由 |
|------|---------|
| 无 | 本次 brainstorming 中，AI 的设计建议均合理，没有需要推翻的。 |

**人工干预 - 设计决策偏离：舍去 WebUI**

项目最终定位为纯 CLI 项目，舍去 WebUI 相关部分。原始交付要求（§6.11）中提到"必须提供 WebUI 接口"，但经过分析，本项目核心目标是构建 harness 的工程机制（主循环、治理、反馈闭环），这些机制均可通过 CLI 交互完整呈现：
- HITL 审批在终端中通过 `readline` 实现，无需 Web 界面
- 审计日志、状态查询等均通过 CLI 命令完成
- 纯 CLI 降低了架构复杂度，让团队聚焦于核心机制实现

此偏离需在最终 REFLECTION.md 中给出解释。

## 四、Brainstorming 技能反思

### 做得好的地方

1. **一问一答的节奏控制**：每次只问一个问题，不会让人感到 overwhelmed。这比一次性抛出 10 个问题然后等回答要好得多。
2. **先收敛再展开**：前三个问题（形态→语言→供应商）快速收敛了项目边界，后续问题才深入细节。顺序合理。
3. **多方案对比**：架构设计阶段给出了三个方案并附推荐理由，而不是直接给一个"最优解"。
4. **逐段审查**：设计分 4 段呈现，每段等待确认后再继续。这避免了"一次性呈现全部设计后需要大幅返工"的风险。

### 让我不满的地方

1. **记忆系统问题未主动提示约束差异**：AI 在问"记忆系统做到什么程度"时，没有主动提示"非重点维度不需要从零实现"。这个规则是我自己从原文中发现的。如果 AI 能在提问时附带规则说明，会更好。
2. **缺少明确的"下一步"指引**：brainstorming 技能在呈现完设计后直接问"是否 OK"，但没有明确告知"确认后将进入 writing-plans 阶段"。对新用户来说，如果能预告后续流程会更好。

### 5.3 冷启动发现的问题

|------|---------|---------------------------|---------|
| 1 | `deepMerge` 函数泛型约束 `T extends Record<string, unknown>` 无法接受 `AgentConfig` 类型（该接口无索引签名），导致 TypeScript 编译错误 TS2739 + TS2345 | 两者皆非——这是 PLAN 中未提供实现细节导致的正常实现问题。PLAN 只说"深度合并"，未指定具体实现方式，agent 首次选择的泛型方案不兼容 | 将 `deepMerge` 改为 `any` 类型的简单实现。已在 PLAN 中无需修订（属于实现细节） |
| 2 | SPEC §3.8 描述凭据存储主方案为操作系统钥匙串（keytar），但 Task 3 的 `AgentConfig` 接口中不含凭据相关字段。agent 暂停确认了"配置系统不涉及凭据管理"的理解是否正确 | SPEC 写对了但信息分散——凭据管理在 §3.8 和 Task 20，配置系统在 §3.7 和 Task 3，两者职责边界在两处分别描述，agent 需要自行推断分界 | 建议在 PLAN Task 3 的描述中加一句"本 Task 仅处理 YAML 配置加载，不涉及凭据管理（凭据见 Task 20）"，减少冷启动 agent 的认知负荷 |
| 3 | SPEC 和 PLAN 均使用"深度合并"一词，但未定义合并策略——数组是替换还是拼接？嵌套对象合并到第几层？agent 选择了"数组替换、无限递归合并"，若主 agent 预期不同行为，可能导致后续集成问题 | SPEC 不够精确——"深度合并"是一个模糊术语 | 建议在 SPEC §3.7 或 PLAN Task 3 中补充："深度合并：嵌套对象递归合并，数组直接替换（非拼接），仅当 source 字段非 undefined 时才覆盖 target 字段" |
