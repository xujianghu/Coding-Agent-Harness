# 反思报告（REFLECTION.md）

---

## 一、哪些 Superpowers 技能发挥了最大作用、哪些「形式大于实质」

在这个项目里，我觉得 `using-git-worktrees` 对我最实用：它让我把不同功能各自开一个 worktree 并行推进、互不干扰，代码干净、随时可回滚。相比之下，`brainstorming` 更偏形式大于实质。它确实能带着我构思需求和项目，但问题在于它预设需求能在开始前就完全敲定，而真实开发中想法难免会变、会冒出新想法。比如我最初 brainstorm 出来的是一次性任务执行器，后来上手觉得不符合预期，才改主意做成交互式对话 CLI——这是 brainstorming 阶段预见不到的方向，等于推翻了最初的用户故事；memory、feedback 两套系统更是建了之后又整个删掉。对比之下，`using-git-worktrees` 发挥了较大作用，而 `brainstorming` 有些形式大于实质。

## 二、TDD 强制在 AI 协作下是阻碍还是放大器

对我而言是放大器。写测试这个动作，会强制我先想清楚接口、边界和预期行为，而不是马马虎虎就上手。一个具体的例子是 `loop.test.ts`：我先定义了 `parseResponse` 三态（`action` / `done` / `text`）的预期行为，才逼出了这个接口的设计——先写测试时根本没法含糊，因为断言要求我明确「输入什么、输出什么」。

## 三、subagent-driven 工作流让智能体能自主运行多久而不偏离主题

我派过 subagent，最大的体会是：它只适合边界清晰、可独立验证的任务。一旦任务跨多个模块、依赖我脑中的共享上下文，subagent 就容易跑偏——因为它没有我在 brainstorming 阶段沉淀下来的隐性上下文。所以我后来把 subagent 限制在「一个模块加上它的测试」这种粒度，让它在一个会话内能独立闭环。

## 四、什么样的 task 颗粒度最优

我认为理想的 task 颗粒度是「一个模块或文件加上它的测试」，大约 100–300 行，能在一次 subagent 会话内完成并验证。颗粒度太大，subagent 容易失控；颗粒度太小，派发成本会超过收益。

## 五、SPEC / PLAN 质量如何影响实现质量

我觉得最能说明这个问题的是 DeepSeek 裸换行 JSON 的案例。spec 里，主循环把「解析 LLM 动作」写成了一个 `JSON.parse` 的一行，设想是 LLM 返回规范 JSON 就行。但接入真实 DeepSeek 后，它在写文件时 `content` 字段里塞了多行代码，用的是**真正的换行符**而不是 `\n` 转义，导致 JSON 非法、反复报 `unparseable response`。我先是从混合文本里提取内嵌 JSON，再把裸换行替换成 `\n`——这些是治标，每补一个 case 又冒出新的 case。最后我改用原生 function calling，让 LLM 直接返回结构化的 `toolCalls`，不再解析 JSON 文本，转义问题才整体消失。这个案例的教训是：spec 当初低估了 LLM 输出的不可控性，把「约束一个模糊系统输出结构化结果」错当成「解析一个字符串」；字符串打补丁是治标，换成结构化接口才是治本。

## 六、最有效的 prompt / context 策略是什么、为什么有效

对我最有效的是「给足上下文」——把工具列表和参数说明写进 system prompt。LLM 需要一份明确的能力清单和参数，才能正确地选动作、填参数，而不是一句模糊的「你可以调用工具」。反过来，抽象的安全提醒基本没用——这正好呼应了「机制必须是代码而不是提示词」：真正管住危险操作的是代码里的 guardrail，而不是 prompt 里一句「注意安全」。

## 七、凭据与分发这两条工程要求，迫使你想清楚了哪些原本会忽略的问题

最令我印象深刻的是做 AES-256-GCM 加密存储和 Docker 分发，这迫使我想清楚了 `.env` 的明文风险，以及「加密不是免费的」：主密码本身也是需要保管的秘密。命令行 `export` 会进 shell history，`.env` 文件是明文、进程环境可见，所以我选择「加密文件 + 主密码」而不是纯环境变量。此外还要管泄露面：`.gitignore` 挡住 `credentials.*` / `.env` / `*.key`，`key status` 只显示 configured、不回显明文，分发之后别人怎么安全地配置自己的 key——这些问题在写代码之前我大概率根本没想过。

## 八、如果重做你会改变什么

如果让我重做，我会一开始就用原生 function calling，而不是 JSON 文本解析。这样能直接避开 JSON 解析的全部弯路（裸换行、混合内容、内嵌提取）。

## 九、你对 Superpowers 这套方法论的批判——它假设了什么，这些假设在你的项目里成立吗

Superpowers 有效的前提是「在开始之前就构思好全貌」，否则就会一直增增改改。brainstorming → writing-plans 流程隐含一个假设：需求能在一开始就被充分想清楚、并敲定成 spec。但这个假设在此项目的开发过程里并不成立——对话模式的需求是后来才浮现的，memory / feedback 建了又删，function calling 是中途才引入的。这些不是 spec 没写清，而是一开始没能完全弄清要什么。所以我觉得：这套方法论需要在开始前就弄清项目、弄清边界；一旦遇到探索性、需求本身还在演化的项目，它的 spec 冻结假设就会失效，只能接受边做边改的成本——就像我这次所做的项目一样。

## 十、我对 harness 工程的理解

做完这个项目，我对课上所说的「Agent = LLM + Harness」有了更加具体的理解。LLM 本身只是「决定下一步做什么」，真正让一个 agent 稳定可靠工作的，是 harness 那层工程：如何组织上下文、怎么分发工具、怎么在危险动作执行前拦截、怎么把测试失败回灌给模型。这些都不是 LLM 能自己完成的，恰恰是软件工程师的价值所在。其中最让我有体感的是要求中所说的「机制必须是代码，而不是提示词」——在开发过程中，我踩过「抽象的安全提醒根本没用、只有 guardrail 代码才拦得住危险命令」的坑；而「移除真实 LLM 后机制还能用 mock 单测验证」这个判据，更是让我真正分清了什么算工程、什么只是写给模型看的提示词。

在 harness 之中，邵院长那天上课所讲的 agent 主循环是整个 harness 的核心骨架：组织上下文 → 调用 LLM → 解析动作 → 分发执行 → 回灌结果 → 停机判断。这个循环把「LLM 只决定下一步做什么」这个单点动作，扩成一个能持续闭环工作的系统。这个循环的每一步都是用代码实现的确定性机制——解析动作是 `parseResponse` 的三态（action / done / text），分发执行走 `executeAction` 加治理管道，回灌结果用 `appendTurnMessages`——而不是写在提示词里的一句要求。
